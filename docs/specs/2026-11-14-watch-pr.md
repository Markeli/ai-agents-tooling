# Sandbox: the bot watches its PRs/MRs for review and CI until they are merged

- Status: Implemented
- Date: 2026-11-14
- ADRs: [0004](../adr/0004-build-the-sandbox-image-from-the-repository-skills-too.md) (introduced: the image is built
  from `skills/claude-code` too), [0001](../adr/0001-version-the-sandbox-image-from-its-changelog.md)

## Problem and goal

The bot (`markeli-agent`) opens a PR/MR, and the owner reviews it: leaves inline threads and top-level comments,
requests changes, or CI fails. Today the bot sees none of this until the owner switches to the terminal and tells it
to look. A review round then costs the owner a context switch and a prompt, even though the work itself is usually
mechanical.

Goal: after the bot opens a PR/MR it notices, within about 30 seconds and without the owner's prompt, every new comment
of the owner (top-level, a new inline thread, or a reply in an existing thread, including one the bot already answered),
every review with a body or verdict, and every failed CI check. It then does the work, pushes, and replies in the
threads. It stops watching when the PR/MR is merged or closed and waits for the next command. Checking costs no model
tokens: a deterministic script polls the API, and the bot is only woken when there is something to act on.

## Scope

In scope:

- A `watch-pr` Claude Code skill: `SKILL.md` and a `watch-pr` shell script that polls one PR/MR and prints one line
  per new event, for GitHub (`gh`) and GitLab.com (`glab`).
- An allow-list of the people and bots whose comments and reviews wake the bot, shipped in the image.
- A rule in the bot's instructions to start a watcher for every PR/MR it opens, and how to handle the events.
- Packaging the skill into the sandbox image, tests for the script, and the image CHANGELOG entry.

Out of scope (non-goals):

- Reacting to people or bots outside the allow-list. Only the owner is on it at first; a bot such as Copilot review
  or CodeQL wakes the bot once its login is added.
- Reacting to a thread being resolved, a label, an assignee, reviewers being added or removed, or a push by someone
  else.
- Watching while the sandbox or the Claude Code session is not running: a watcher lives in the session that started it.
  After a restart the owner resumes it with `/watch-pr`.
- Webhooks or any service outside the sandbox; GitHub's PR activity subscription of cloud sessions (it is GitHub-only
  and isn't available in sbx).
- Merging, approving, or closing anything: the hard git rules stay as they are.
- A limit on how long a watch runs: it ends only with merge or close.

## Requirements

### Starting a watch

1. After the bot opens a PR/MR, it starts a watcher for it without being asked. It runs one watcher per PR/MR it
   opened in the session.
2. `/watch-pr [<url>|<number>]` starts a watcher by hand. A URL picks the PR/MR directly. A number is a PR/MR of
   the repository in the current directory. Without an argument it is the open PR/MR of the current branch
   (`gh pr view` / `glab mr view`). GitHub or GitLab is chosen by the URL's host, or else by the host of `origin`.
3. Starting a watcher for a PR/MR that already has one in the session is a no-op that says so.
4. A watcher runs as a `Monitor` of the Claude Code session (`timeout_ms` at its 30-minute maximum). The script ends
   itself before the monitor would expire: after `--max-runtime` (default 25 minutes) it exits 3, and the bot starts it
   again with the same arguments. The script's state makes the restart invisible: no event is reported twice, and none
   is lost between the two runs. If a monitor expires anyway, the bot restarts it the same way.

### What counts as an event

5. The script polls every 30 seconds (`--interval` overrides it) and prints one line per new event:
   - `comment`: a top-level comment on the PR/MR by an allow-listed author;
   - `thread`: a new inline thread (diff comment) by an allow-listed author;
   - `reply`: a new comment by an allow-listed author in an existing thread, whoever started it and whether or not
     the bot already answered in it;
   - `review`: a verdict or summary of an allow-listed author. GitHub: a review that is `CHANGES_REQUESTED`, or
     `APPROVED` or `COMMENTED` with a non-empty body. GitLab: the author's reviewer state on the MR
     (`merge_requests/:iid/reviewers`) changed to `requested_changes` or `approved`, reported once per change; the
     comments of a submitted GitLab review are notes and come as `comment`/`thread`/`reply`. On both hosts the inline
     comments of a review are reported as `thread`/`reply` on their own;
   - `ci-failed`: a check of the PR/MR's head commit finished as failed, whoever's it is (GitHub: a check run or
     commit status of the head commit with a failing conclusion; GitLab:
     the MR's head pipeline status `failed`, with the names of its failed jobs). Reported once per check (GitHub:
     check name and head SHA; GitLab: pipeline ID); a re-run that fails again on the same commit isn't reported again;
   - `merged`, `closed`: the PR/MR was merged or closed. The script prints this line and exits 0.
6. Resolving a thread, editing or deleting a comment, GitLab system notes, cancelled or skipped checks, and anything by
   an author outside the allow-list, and the session's own comments (requirement 7) are not events.
7. The allow-list is a file in the image, `/etc/claude-code/watch-pr/authors`, one `<host> <login>` per line (`#`
   comments allowed). A login is a person or a bot account: a GitHub App's comments come from `<app>[bot]` (e.g.
   `github.com copilot-pull-request-reviewer[bot]`), a GitLab bot is a user like any other. Logins compare
   case-insensitively. The image ships the owner's logins that `source-control.md` requests review from,
   `github.com Markeli` and `gitlab.com markeli`, and nothing else. `--authors <file>` replaces the file (tests,
   trials).

   The bot's own account can be on the allow-list: the owner plans separate roles, such as a coder and a reviewer,
   running as `markeli-agent` in different sessions. A session must then not wake itself with its own replies, so:
   - every comment, reply and review body the bot posts ends with a hidden marker naming its session,
     `<!-- watch-pr session=<CLAUDE_CODE_SESSION_ID> -->` (an HTML comment, rendered by neither GitHub nor GitLab);
   - a comment or review by `markeli-agent` is an event only if it carries a marker of another session. One with this
     session's marker, or with no marker at all, is not: a forgotten marker costs a missed event, never a loop of the
     bot answering itself;
   - comments of other allow-listed authors are events with or without a marker.

   Roles themselves (prompts, which session reviews what) are out of scope. GitHub doesn't let a PR's author approve
   it or request changes on it, so a reviewer session using the same account reviews with comments and `COMMENTED`
   reviews.

### First run and catch-up

8. The script keeps its state per Claude Code session and PR/MR, in
   `${XDG_STATE_HOME:-$HOME/.local/state}/watch-pr/<session>/<host>/<project>/<number>.json`: the IDs of comments
   and reviews already seen, the GitLab reviewer states, the failed checks already reported, and the last poll time.
   `<session>` is `--session`, by default `$CLAUDE_CODE_SESSION_ID`; without either the script exits 2. Sessions
   therefore never share state: a resumed session (`claude --resume`) keeps its state, a new one starts with none. On
   `merged`/`closed` the script deletes its state file; at start it deletes state directories untouched for 30 days.
9. Without a state file (the first watch of a PR/MR in this session, e.g. `/watch-pr` after a restart), the first poll
   reports what is still waiting for the bot, then records everything as seen:
   - comments and reviews of allow-listed authors other than `markeli-agent` created after the bot's latest activity
     on the PR/MR (the latest comment or review of `markeli-agent`, from any session, or the head commit's commit
     date if it is later). The bot's own comments are never caught up: a new session can't tell an earlier session of
     its own from a reviewer session, so comments a reviewer session left while no coder session watched are missed;
     the owner points the new session at them. GitLab reviewer states aren't caught up either: the API doesn't say
     when a state changed;
   - checks of the head commit that have already failed.
   Nothing is reported for a PR/MR the bot just opened.

### Output and failures

10. An event line is `watch-pr <ref> <kind> <author> <url> <excerpt>`: `<ref>` is `owner/repo#N` (GitHub) or
    `group/project!N` (GitLab); `<url>` links the comment, review, check or pipeline; `<excerpt>` is the first 200
    characters of the body on one line (for `ci-failed` the check's name, in a strict charset since any CI app writes
    it; `-` for `merged`, `closed`). The bot fetches the full text
    itself when it acts.
11. Only event lines go to stdout, so each line wakes the bot. Diagnostics go to stderr.
12. A failed request is retried at the next poll. After 10 consecutive failed polls (about 5 minutes) the script prints
    one `watch-pr <ref> warning - - <reason>` line and keeps polling. It prints another one only after a poll has
    succeeded in between.
13. A 401, 403 or 404 for the PR/MR itself is fatal: the script prints `watch-pr <ref> error - - <reason>` and exits 1.
    The bot reports it and doesn't start the watcher again (hard git rule: stop on authentication errors).
14. Invalid arguments, an unknown host, no PR/MR for the current branch, or missing `gh`/`glab`/`jq` make the script
    exit 2 with a message on stderr, before it starts polling.

### What the bot does with events

15. The bot fixes a PR/MR on its own branch without disturbing other work. If the main working copy has that branch
    checked out, it works there. Otherwise it uses a `git worktree` for the branch outside the working copy (e.g.
    `~/worktrees/<repo>/<branch>`), created at the first event, reused for later ones, and removed after `merged` or
    `closed`. Work in progress in the main working copy, committed or not, is never stashed, switched or mixed in.
16. On `comment`, `thread`, `reply`, `review` or `ci-failed`, the bot reads the full comment or the failed job's log,
    makes the changes it agrees with, commits them as new commits, pushes, and replies in the thread (a top-level
    comment: a top-level reply) with what it changed. It follows the source-control rules and the
    `superpowers:receiving-code-review` approach: no change it can't justify.
17. When a comment is a question, is unclear, or the bot disagrees, it answers in the thread and also writes a short
    message in the terminal: the PR/MR, the thread link, and what it asked or why it disagrees. It doesn't block the
    other events while waiting for an answer.
18. Events never interrupt work in progress: the bot finishes what it is doing, including a task the owner gave it in
    the terminal, then handles the events that arrived meanwhile, in order.
19. On `merged` or `closed` the bot says so in one line and does nothing more for that PR/MR.

Non-functional:

1. No model tokens are spent while nothing happens, beyond a restart of the watcher every 25 minutes.
2. The owner runs several sandboxes at once, and every watcher in every one of them polls with the same
   `markeli-agent` token, so they share its rate limits:
   - GitHub: one GraphQL query per poll fetches everything requirement 5 needs (state, head commit and its check
     rollup, comments, review threads with their comments, reviews) and the token's `rateLimit`; further pages only
     when a PR has more than 100 items of a kind. A query costs 1 point of the 5000 points/hour GraphQL limit, so a
     watcher spends ≈ 120 points/hour and 40 watchers fit, without touching the REST limit `gh` and `git` use for the
     bot's own work.
   - GitLab: three requests per poll (the MR, its notes, its reviewers), plus the failed jobs when a pipeline fails,
     against GitLab.com's per-user limit of 2000 authenticated requests per minute.
   - When the remaining GitHub budget falls below 20% of the limit, the script polls every 5 minutes until the reset
     and says so once on stderr, so many watchers slow down instead of starving the bots' work.
3. The script needs only what the image already has: `bash`, `gh`, `glab`, `jq`.
4. The script never writes to the PR/MR. Replies and pushes are the bot's, under its usual rules.

## Acceptance scenarios

```gherkin
Scenario: A reply in a thread the bot already answered wakes it
  Given the bot opened a PR, the owner left an inline comment, the bot fixed it and replied in the thread
  When the owner resolves another thread and replies in this one
  Then within a poll interval the watcher prints one "reply" line for the owner's reply
  And nothing for the resolved thread
  And the bot makes the change, pushes and replies in that thread

Scenario: CI fails on the bot's push
  Given a watcher on a PR whose head commit's "build" check fails
  Then the watcher prints one "ci-failed" line for "build"
  And re-running the failed check on the same commit prints nothing more

Scenario: Merge ends the watch
  Given a watcher on a PR
  When the owner merges it
  Then the watcher prints a "merged" line and exits 0
  And the bot says the PR is merged and waits for a command

Scenario: Resume after a sandbox restart
  Given the owner commented on the bot's MR while the sandbox was stopped
  When the owner runs /watch-pr on the MR's branch in a new session
  Then the first poll prints the comments posted after the bot's latest comment or commit
  And later polls print only new events

Scenario: Only allow-listed authors wake the bot
  Given a watcher on a PR, and an allow-list with the owner and "copilot-pull-request-reviewer[bot]"
  When CodeQL or another person comments
  Then the watcher prints nothing
  When Copilot review leaves an inline comment
  Then the watcher prints a "thread" line for it

Scenario: A reviewer session wakes the coder session, and nobody wakes itself
  Given "markeli-agent" is on the allow-list, and a coder session watches its PR
  When a reviewer session of "markeli-agent" comments with its own session marker
  Then the coder's watcher prints a "comment" line
  When the coder session replies with its session marker
  Then the coder's watcher prints nothing

Scenario: GitLab request changes
  Given a watcher on an MR
  When the owner submits a review with two comments and "Request changes"
  Then the watcher prints the two comments and one "review" line with "requested_changes"
```

## Contracts

```text
watch-pr [<url>|<number>] [--interval <seconds>] [--authors <file>] [--session <id>] [--state-dir <dir>]
         [--max-runtime <seconds>] [--once]

stdout   watch-pr <ref> <kind> <author> <url> <excerpt>
         kind: comment | thread | reply | review | ci-failed | merged | closed | warning | error
exit     0 merged or closed; 1 fatal API error; 2 usage or environment error; 3 --max-runtime reached, restart me
--once   one poll, then exit 0 (tests and debugging)
--max-runtime   default 1500 seconds
```

- `/etc/claude-code/watch-pr/authors`: `<host> <login>` per line.
- Skill: `/watch-pr [<url>|<number>]` in the image's managed skills directory,
  `/etc/claude-code/.claude/skills/watch-pr/`
  (sbx mounts its own store over `~/.claude/skills`).
- `sandbox/image/rules/source-control.md`: after opening a PR/MR, start `watch-pr` for it (requirements 1, 15–19);
  end every PR/MR comment, reply and review body with the session marker (requirement 7).
- Session marker: `<!-- watch-pr session=<id> -->`, the last line of the body.

## Edge cases and failure modes

- A PR/MR with more than 100 comments → GitHub: the query reads the newest 100 of each kind, and fewer than 100 new
  ones arrive between two polls, so nothing new is missed; only a catch-up over more than 100 waiting items of one
  kind drops the oldest. GitLab: discussions and jobs are paged.
- The owner edits a comment the bot already handled → not an event (requirement 6); the owner replies instead.
- The bot pushes, and the new head commit's checks are still running → nothing until one of them fails.
- A GitLab MR without a pipeline → no `ci-failed` events.
- The PR/MR is already merged or closed at start → the first poll prints `merged`/`closed` and the script exits 0.
- Two sessions watch the same PR/MR → each has its own state and reports every event, so both bots would act on it;
  watching a PR/MR from one session at a time is the owner's call. Within a session the script holds an `flock` on the
  PR/MR's state while it runs, and a second watcher exits 2 with a message. The kernel drops the lock when the process
  dies, so a crashed session leaves none behind, and a restart after exit 3 never meets its predecessor.
- The clock in the VM is skewed → the catch-up compares API timestamps with each other only, never with the local
  clock.

## Test plan

- Script tests, in the style of `.github/scripts/tests/run.sh`: stub `gh` and `glab` that serve recorded JSON
  fixtures, with `--once` and a temporary `--state-dir`. They cover every event kind on both hosts (GitLab reviewer
  states included), the allow-list (case-insensitive, a `[bot]` login, others ignored), `markeli-agent` comments
  with another session's marker, this session's marker and no marker, state per
  session, the slow-down below 20% of the GitHub budget, no repeats across runs, catch-up on the first run, a failed
  check reported once per head SHA, merged/closed exit 0, transient failures and the warning, 401/403/404 exit 1, and
  usage errors exit 2.
- CI runs the tests and `shellcheck` on the script in the `lint` job of `sandbox-image.yml`.
- A manual run on the host's sandbox before release: open a PR, comment, reply in an answered thread, resolve a
  thread, fail a check, merge; the same on a GitLab MR.

## Rollout

- Released as a minor image version (a new skill and rule, nothing removed), with a CHANGELOG entry.
- Existing sandboxes get it when recreated on the new image (`agent-sandbox --recreate`).

## Packaging

- The skill's source is `skills/claude-code/watch-pr/` (`SKILL.md`, the `watch-pr` script, its tests and fixtures).
- Per [ADR 0004](../adr/0004-build-the-sandbox-image-from-the-repository-skills-too.md), the image is built with
  `skills/claude-code` as a second build context, copies every skill there into `/etc/claude-code/.claude/skills/`,
  and is addressed by a `git mktree` of `sandbox/image` and `skills/claude-code`. `sandbox-image-plan.sh`, its tests,
  `sandbox-image.yml` (path filters, `build-contexts`) and `sandbox/README.md` change accordingly; a PR that changes
  `skills/claude-code` needs an image CHANGELOG entry.
- The allow-list `sandbox/image/watch-pr/authors` is copied to `/etc/claude-code/watch-pr/authors`. The script is
  on `PATH` as `watch-pr`.
- `AGENTS.md`'s structure line for `sandbox/` and `skills/` says that `skills/claude-code` ships in the image.
