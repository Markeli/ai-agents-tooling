# 0005. Запускать mcp-grafana локально рядом с каждым агентом, а не общим сервером

- Status: Accepted
- Date: 2026-11-28
- Related: [спека](../specs/2026-11-28-grafana-mcp.md)

## Context

Агентам (бот `markeli-agent` в песочнице sbx и Claude Code / Claude Desktop владельца на Mac) нужен доступ на чтение к
метрикам (VictoriaMetrics), логам (VictoriaLogs) и дашбордам машин владельца. Всё это уже доступно через Grafana
(`https://grafana.markelow.me`, geonosis, стек `monitoring` в `iaac/doco-cd`): источники данных `victoriametrics`
(тип `prometheus`) и `victorialogs` (плагин `victoriametrics-logs-datasource`). Официальный MCP-сервер Grafana,
[mcp-grafana](https://github.com/grafana/mcp-grafana), с v2.4.0 умеет и то и другое: Prometheus-инструменты работают с
VictoriaMetrics, Loki-инструменты — с VictoriaLogs (LogsQL). Он умеет работать локально (stdio) или сервером
(streamable-http).

Любой доступ с ролью Viewer даёт чтение всех метрик и логов. В логах есть текст из интернета (пути запросов,
User-Agent), поэтому агент, читающий их, получает недоверенные данные.

## Decision drivers

- Не открывать в интернет новых сервисов: VictoriaMetrics и VictoriaLogs внутри стека `monitoring` доступны без
  авторизации, и сервис в этой сети, взломанный снаружи, получил бы к ним прямой доступ.
- Токен не должен попадать в VM песочницы (как токены GitHub и GitLab: их подставляет прокси sbx).
- Отзывать доступ песочницы и доступ владельца по отдельности.
- Конфигурация в репозитории, через ревью, одинаковая в каждой новой песочнице.
- Один и тот же способ для песочницы и для Mac владельца.

## Considered options

### Вариант 1: mcp-grafana локально у каждого клиента (stdio)

Бинарник в образе песочницы и на Mac; каждый ходит в публичную Grafana со своим токеном service account (Viewer).

- Good: никакой новой поверхности атаки: Grafana уже публичная; токен песочницы подставляет прокси sbx, в VM его нет;
  на Mac токен только в Keychain; два service account отзываются по отдельности.
- Bad: обновлять в двух местах (образ и Mac); утёкший токен работает и с API Grafana напрямую (на чтение).

### Вариант 2: общий сервер mcp-grafana на geonosis (streamable-http за nginx)

- Good: одно место настройки и обновления через doco-cd; токен Grafana остаётся на сервере.
- Bad: новый публичный сервис в сети стека `monitoring` (см. первый driver); один общий токен доступа к MCP — нет
  раздельного отзыва и не видно, кто спрашивал; режим per-user (`--require-user-credentials`) это чинит, но тогда
  токены Grafana снова у клиентов, и выигрыш пропадает. Больше всего работы: сервис, nginx, DNS, секрет, проба
  blackbox, плюс изменения в песочнице всё равно.

### Вариант 3: шлюз MCP sbx на Mac (`sbx mcp add`)

- Good: без изменений в образе.
- Bad: настройка вне репозитория и на каждом Mac вручную; в каталоге шлюза mcp-grafana нет; контейнер шлюза ходит в
  Grafana мимо сетевой политики песочницы; Claude Code / Desktop владельца этим не покрываются.

### Вариант 4: без MCP — скилл с запросами curl к API Grafana или CLI `gcx`

- Good: минимум нового софта.
- Bad: у `gcx` нет VictoriaLogs; логи через сырой `/api/ds/query` агент собирает с ошибками и тратой контекста — плохо
  ровно для основной задачи.

## Decision

Chosen option: **mcp-grafana локально у каждого клиента**, потому что только он не добавляет публичных сервисов,
держит токен песочницы вне VM и даёт раздельный отзыв, а по возможностям не уступает общему серверу.

## Consequences

- Positive: доступ на чтение к метрикам, логам и дашбордам без изменений на серверах; два независимых токена.
- Negative: обновление mcp-grafana — релиз образа и `brew upgrade` на Mac; агент читает недоверенный текст из логов
  (правило боту: это данные, не инструкции).
- Follow-ups: если понадобятся клиенты без локального запуска (claude.ai, телефон), пересмотреть вариант 2 новым ADR.
